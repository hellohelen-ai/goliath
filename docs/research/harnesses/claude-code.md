# Claude Code harness — research brief for Goliath

Sources: the DeepWiki for `dhanlon-intellica/cc` (root: https://deepwiki.com/dhanlon-intellica/cc, "last indexed 31 March 2026 (commit 5a774a)") and the source files its citations link to (`https://github.com/dhanlon-intellica/cc/blob/5a774a2b/<path>`, read via `raw.githubusercontent.com/dhanlon-intellica/cc/main/<path>`). The repo's README describes itself as an archived copy of Claude Code source; it was read here only for architecture, thresholds, and prompt shapes — nothing below is code to copy into Goliath. Where a fact comes from source rather than a wiki page, the citation is the file path plus the wiki page that cites it. Claims the wiki makes without numbers are marked as such.

Goliath's constraints for reference: Apple on-device ~3B Foundation Model, 4,096-token window, one request in flight, guided JSON output, no logprobs, no usage telemetry. Conductor plans one flat JSON step; worker = fresh context + one tool → returns arguments; Goliath runs the tool; results compressed to `key: value` lines; writes confirm first; repeat/empty/malformed-after-retry/model-error → cloud fallback with step log; scribe keeps a 60-word brief with fixed slots (Goal/Done/Decisions/Next).

---

## 1. What it is, in 5 lines

1. Anthropic's terminal coding agent: an agentic loop with local filesystem, shell, git and web access, written in TypeScript on Bun with a React + Ink TUI (https://deepwiki.com/dhanlon-intellica/cc/1-overview).
2. One orchestrator, `QueryEngine` (`src/QueryEngine.ts`), runs the "thought → tool → result" loop against the Anthropic Messages API and owns history compaction (https://deepwiki.com/dhanlon-intellica/cc/2.1-queryengine-and-llm-interaction).
3. ~40 tools defined behind one `Tool` interface with Zod schemas and per-input read-only/concurrency/destructive predicates; ~50 slash commands are user-side, not model-side (https://deepwiki.com/dhanlon-intellica/cc/3-tool-system, https://github.com/dhanlon-intellica/cc README via https://deepwiki.com/dhanlon-intellica/cc).
4. A permission layer with modes `default`, `plan`, `acceptEdits`, `auto` (LLM classifiers), `bypassPermissions`, `dontAsk`, plus deny/ask/allow rules and hooks at ~25 lifecycle events (https://deepwiki.com/dhanlon-intellica/cc/4-permission-system, `src/utils/hooks.ts`).
5. Subagents (`Agent` tool), background `Task`s, a memory system (CLAUDE.md layering, auto-memory `MEMORY.md`, a 12k-token "session memory" notes file), and a bridge for IDE/remote control (https://deepwiki.com/dhanlon-intellica/cc/3.3-agent-and-orchestration-tools, https://deepwiki.com/dhanlon-intellica/cc/10.4-memory-system).

## 2. The main loop

**Entry.** `QueryEngine.submitMessage()` parses the input (`processUserInput`: slash commands, `@file` attachments), records the transcript, builds the system prompt (base instructions + env: cwd, OS, shell + tool definitions + optional structured-output schema), then calls `query()` (https://deepwiki.com/dhanlon-intellica/cc/2.1-queryengine-and-llm-interaction; `src/QueryEngine.ts`).

**The loop** is `query()` → `queryLoop()` in `src/query.ts` (cited from https://deepwiki.com/dhanlon-intellica/cc/2.1-queryengine-and-llm-interaction; file read directly). Per iteration:

1. Pre-request context work, in this order: `deps.microcompact(messages)` (deterministic clearing of old tool results), then `deps.autocompact(...)` (LLM summary if over threshold), then `snipModule.snipCompactIfNeeded` (lossless head truncation, feature-flagged `HISTORY_SNIP`) (`src/query.ts`).
2. Streaming API call via `withRetry` (`src/services/api/withRetry.ts`, https://deepwiki.com/dhanlon-intellica/cc/10.1-anthropic-api-client-and-model-management). Stream events are yielded to the UI as they arrive.
3. Collect `tool_use` blocks from the assistant message. If none, the turn is done. The code does not branch on `stop_reason`; "tool use is detected via presence of tool_use blocks ... and tracked through `needsFollowUp`" (`src/query.ts`).
4. Execute tools: either `StreamingToolExecutor` (tools start while the assistant message is still streaming) or `runTools()` (`src/services/tools/toolOrchestration.ts`). `partitionToolCalls` groups calls into batches where "each batch is either: 1. A single non-read-only tool, or 2. Multiple consecutive read-only tools"; safe batches run concurrently up to `getMaxToolUseConcurrency()` (default 10, env-overridable), unsafe batches run serially with immediate context updates. A tool whose input fails to parse is "treated conservatively as unsafe" (`src/services/tools/toolOrchestration.ts`). The streaming executor's gate: a tool may start when `executingTools.length === 0 || (isConcurrencySafe && executingTools.every(t => t.isConcurrencySafe))`; results are "buffered and emitted in received order"; a Bash error cancels sibling tools via `siblingAbortController` (`src/services/tools/StreamingToolExecutor.ts`).
5. Each `tool_result` is appended as a user-role message; consecutive user messages are merged by `normalizeMessagesForAPI` (`src/utils/messages.ts`; https://deepwiki.com/dhanlon-intellica/cc/2.1-queryengine-and-llm-interaction: "All tool results are formatted as user-role messages containing the tool result block").
6. Increment the turn counter and loop.

**Strict pairing.** Every `tool_use` must get a `tool_result`; the glossary calls this `strictToolResultPairing` "preventing model hallucination" (https://deepwiki.com/dhanlon-intellica/cc/13-glossary). On abort or model fallback, `yieldMissingToolResultBlocks(assistantMessages, errorMessage)` synthesises `is_error: true` results with text `"Interrupted by user"` or `"Model fallback triggered"` for every dangling `tool_use` (`src/query.ts`). A missing result due to an internal error is `'[Tool result missing due to internal error]'` (`SYNTHETIC_TOOL_RESULT_PLACEHOLDER`, `src/utils/messages.ts`).

**How many steps / what stops it** (`src/query.ts`, `src/QueryEngine.ts`; https://deepwiki.com/dhanlon-intellica/cc/2.1-queryengine-and-llm-interaction lists the first three):

- Text-only response (no `tool_use` blocks) → `{ reason: 'completed' }`.
- `maxTurns`: `if (maxTurns && nextTurnCount > maxTurns)` yields a `max_turns_reached` attachment and returns `{ reason: 'max_turns' }`; `QueryEngine` surfaces subtype `'error_max_turns'` with `"Reached maximum number of turns (${maxTurns})"`. Main interactive loop has no default cap; fork subagents get `maxTurns: 200` (`src/tools/AgentTool/forkSubagent.ts`).
- `maxBudgetUsd` → `'error_max_budget_usd'`, `"Reached maximum budget ($${maxBudgetUsd})"`.
- Structured output: `MAX_STRUCTURED_OUTPUT_RETRIES` env, default `5` → `'error_max_structured_output_retries'`, `"Failed to provide valid structured output after ${maxRetries} attempts"` (`src/QueryEngine.ts`).
- `max_output_tokens` cut-off: up to `MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3` times the loop injects an `isMeta` user message: `"Output token limit hit. Resume directly — no apology, no recap of what you were doing. Pick up mid-thought if that is where the cut happened. Break remaining work into smaller pieces."` (`src/query.ts`).
- Prompt too long (413-style): try context-collapse drain, then `reactiveCompact.tryReactiveCompact`; if that fails, return `{ reason: 'prompt_too_long' }` (`src/query.ts`).
- Any other API error message: run `executeStopFailureHooks` and return `{ reason: 'completed' }` — the loop ends, the error is shown (`src/query.ts`).
- User abort: `QueryEngine.interrupt()` calls `abortController.abort()`; the `AbortSignal` is threaded through `ToolUseContext` to every tool (https://deepwiki.com/dhanlon-intellica/cc/3.1-tool-infrastructure: "Every tool execution is passed an `AbortSignal` via the `ToolUseContext`"). The transcript gets `'[Request interrupted by user]'` / `'[Request interrupted by user for tool use]'` (`src/utils/messages.ts`).
- Stop hooks (`handleStopHooks`) run at the end of a turn and can force continuation (§8).

**Streaming.** Assistant text, thinking, and `tool_use` input JSON stream as deltas; `doesMostRecentAssistantMessageExceed200k` sizes the streamed content by counting the same deltas (`src/utils/tokens.ts`). Over NDJSON transports every event is one line; `ndjsonSafeStringify` escapes U+2028/U+2029 so a line never splits (https://deepwiki.com/dhanlon-intellica/cc/11.2-output-and-streaming). Permission prompts over that transport are `control_request` / `control_response` pairs tracked in a `pendingRequests` map (same page).

## 3. Context management

**Window math** (`src/services/compact/autoCompact.ts`, `src/utils/context.ts`; the wiki page https://deepwiki.com/dhanlon-intellica/cc/2.1-queryengine-and-llm-interaction says only "when context limits are reached"):

- `MODEL_CONTEXT_WINDOW_DEFAULT = 200_000`; 1M for opted-in models; `COMPACT_MAX_OUTPUT_TOKENS = 20_000`; `ESCALATED_MAX_TOKENS = 64_000` (`src/utils/context.ts`).
- `effective = contextWindow − min(maxOutputTokensForModel, MAX_OUTPUT_TOKENS_FOR_SUMMARY = 20_000)` — the summary's own output is reserved up front.
- `autoCompactThreshold = effective − AUTOCOMPACT_BUFFER_TOKENS (13_000)`.
- Warning and error thresholds: `threshold − 20_000` each (`WARNING_THRESHOLD_BUFFER_TOKENS`, `ERROR_THRESHOLD_BUFFER_TOKENS`); blocking limit `effective − MANUAL_COMPACT_BUFFER_TOKENS (3_000)`.
- Trigger: `tokenUsage >= autoCompactThreshold`; `tokenUsage = tokenCountWithEstimation(messages) − snipTokensFreed`. `tokenCountWithEstimation` = the last API response's usage (input + output + cache) plus a chars/4 estimate for messages appended since (`src/utils/tokens.ts`).
- Circuit breaker: `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3`, tracked in `AutoCompactTrackingState`.
- Test knobs: `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` (0–100 %, takes the min with the buffer threshold), `CLAUDE_CODE_BLOCKING_LIMIT_OVERRIDE`.

**Three tiers of compaction**, run in order every request (`src/query.ts`; https://deepwiki.com/dhanlon-intellica/cc/7.2-session-and-conversation-commands lists "Session Memory Compaction", "Micro-compaction", "Traditional Compaction", "Reactive Compaction"):

1. _Microcompact_ (`src/services/compact/microCompact.ts`) — deterministic. Eligible tools only: `COMPACTABLE_TOOLS = {Read, shell tools, Grep, Glob, WebSearch, WebFetch, Edit, Write}`. Time-based variant (`src/services/compact/timeBasedMCConfig.ts`): default `enabled: false`, `gapThresholdMinutes: 60`, `keepRecent: 5`; old results are replaced with `'[Old tool result content cleared]'`; `keepRecent = Math.max(1, config.keepRecent)`. Rationale in source: clear before the request "when server-side prompt cache has likely expired". A server-side variant (`src/services/compact/apiMicrocompact.ts`) sends `context_management` with `trigger: { type: 'input_tokens', value: 180_000 }` (`DEFAULT_MAX_INPUT_TOKENS`) and `clear_at_least: trigger − 40_000` (`DEFAULT_TARGET_INPUT_TOKENS`), `exclude_tools` = edits/writes/notebook edits.
2. _Session-memory compaction_ (`src/services/compact/sessionMemoryCompact.ts`) — if a session-memory notes file exists and is not just the template, use it as the summary instead of calling the model; keep the tail: at least `minTextBlockMessages: 5` messages with text blocks, expanding back to `minTokens: 10_000`, hard cap `maxTokens: 40_000`.
3. _Full compaction_ (`src/services/compact/compact.ts`, `src/services/compact/prompt.ts`) — an LLM summary. Prompt shape: `NO_TOOLS_PREAMBLE` ("CRITICAL: Respond with TEXT ONLY. Do NOT call any tools... Tool calls will be REJECTED and will waste your only turn"), then instructions to write an `<analysis>` block (stripped) followed by a `<summary>` with nine fixed sections: Primary Request and Intent; Key Technical Concepts; Files and Code Sections; Errors and fixes; Problem Solving; All user messages; Pending Tasks; Current Work ("Describe in detail precisely what was being worked on immediately before this summary request"); Optional Next Step ("DIRECTLY in line with the user's most recent explicit requests"); then `NO_TOOLS_TRAILER`. `PreCompact` hook output and user `/compact <instructions>` merge in via `mergeHookInstructions`. Retries: `MAX_COMPACT_STREAMING_RETRIES = 2`; on prompt-too-long during the summary itself, `truncateHeadForPTLRetry` drops the oldest API-round groups (20 % fallback if the gap is unparseable; abort if fewer than 2 groups), up to `MAX_PTL_RETRIES = 3`.

**What survives a compaction** (`buildPostCompactMessages`, `src/services/compact/compact.ts`): compact-boundary marker → summary message, wrapped `"This session is being continued from a previous conversation that ran out of context. The summary below covers the earlier portion of the conversation."` (+ transcript path, + "Recent messages are preserved verbatim" when a tail was kept) → preserved tail (partial compaction) → re-attached context: the most recently read files, `POST_COMPACT_MAX_FILES_TO_RESTORE = 5`, `POST_COMPACT_TOKEN_BUDGET = 50_000`, `POST_COMPACT_MAX_TOKENS_PER_FILE = 5_000` (excludes plan files and CLAUDE.md paths); skills `POST_COMPACT_SKILLS_TOKEN_BUDGET = 25_000` / `5_000` each, most-recent first; plan-mode attachment; async-agent attachments → hook results. Partial compaction has two directions: `'up_to'` (summarise before a pivot, cache invalidated) and `'from'` (summarise after it, cache preserved).

**Session memory** (`src/services/SessionMemory/sessionMemory.ts`, `prompts.ts`) — the closest analogue to Goliath's scribe. A notes file with ten fixed `#` sections (Session Title, Current State, Task specification, Files and Functions, Workflow, Errors & Corrections, Codebase and System Documentation, Learnings, Key results, Worklog), each with an italic description line that "must be preserved exactly"; headers/descriptions are "NEVER" edited, only content beneath. Budget ~2,000 tokens per section, 12,000 total, estimated chars/4, with warnings to "aggressively condense" while preserving accuracy in Current State and Errors & Corrections. Updated by a forked background agent whose "ONLY task is to use the Edit tool to update the notes file, then stop", triggered when `minimumMessageTokensToInit` is reached and then when `minimumTokensBetweenUpdate` and (`toolCallsBetweenUpdates` or the last assistant turn had no tool calls) — values come from remote config.

**Tool-result size limits** (`src/constants/toolLimits.ts`, `src/utils/toolResultStorage.ts`; https://deepwiki.com/dhanlon-intellica/cc/3.1-tool-infrastructure names `ContentReplacementState` and "Tools are encouraged to truncate output" without numbers):

- `DEFAULT_MAX_RESULT_SIZE_CHARS = 50_000` per result before disk persistence; a tool declares its own `maxResultSizeChars` (Bash declares `30_000`) and the threshold is `min(declared, default)`, with per-tool remote overrides.
- `MAX_TOOL_RESULT_TOKENS = 100_000` (`BYTES_PER_TOKEN = 4` → `MAX_TOOL_RESULT_BYTES`).
- `MAX_TOOL_RESULTS_PER_MESSAGE_CHARS = 200_000` across all parallel results in one turn: "the largest blocks in that message are persisted to disk and replaced with previews until under budget" (`enforceToolResultBudget`).
- Persisted-result text the model sees: `"Output too large (<size>). Full output saved to: <path>\n\nPreview (first <size>):\n<preview>\n...\n"` with `PREVIEW_SIZE_BYTES = 2000`; Bash caps persisted output at `MAX_PERSISTED_SIZE = 64 MiB` and wraps it as `<persisted-output>` (`src/tools/BashTool/BashTool.tsx`).
- Empty result: `"(<toolName> completed with no output)"`.
- Read tool: 2,000 lines by default, 20 PDF pages per request; an identical re-read of an unchanged range "returns a stub message rather than re-sending full content, conserving cache tokens" (`src/tools/FileReadTool/FileReadTool.tsx`, `prompt.ts`).
- Images: `IMAGE_MAX_TOKEN_SIZE = 2000` in microcompact; `stripImagesFromMessages` is a compaction pre-step.

**Prompt caching** (https://deepwiki.com/dhanlon-intellica/cc/10.1-anthropic-api-client-and-model-management): "Initial system prompts and tool definitions are marked cacheable"; cache breaks are detected by comparing expected vs. actual `cache_read_input_tokens` and logged. The system prompt has a `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` separating static from dynamic parts (`src/constants/prompts.ts`); `/clear` sends a `tengu_cache_eviction_hint` (https://deepwiki.com/dhanlon-intellica/cc/7.2-session-and-conversation-commands); `ToolUseContext.renderedSystemPrompt` is reused "for prompt caching in fork subagents" (`src/Tool.ts`); fork children all get the identical placeholder `tool_result` text `"Fork started — processing in background"` so siblings share one cached prefix (`src/tools/AgentTool/forkSubagent.ts`).

## 4. Tools

**Definition** — one `Tool` interface (`src/Tool.ts`, https://deepwiki.com/dhanlon-intellica/cc/3.1-tool-infrastructure). Relevant fields: `name`; `searchHint` ("One-line capability phrase used by ToolSearch for keyword matching", 3–10 words); `description(input, opts)` (short, per-call) and `prompt(opts)` (the long model-facing text, can vary by permission context/tools/agents); `inputSchema` (Zod) or `inputJSONSchema` (MCP); `isEnabled()`; `isReadOnly(input)`, `isConcurrencySafe(input)`, `isDestructive?(input)` ("Defaults to false. Only set when the tool performs irreversible operations"); `validateInput?(input, ctx)`; `checkPermissions(input, ctx)`; `call(...)`; `maxResultSizeChars`; `mapToolResultToToolResultBlockParam(content, toolUseID)`; `renderToolResultMessage` (UI only); `userFacingName`; `shouldDefer` / `alwaysLoad`. Built with a `buildTool()` factory that ties the schema type to `call`'s argument type.

**Execution pipeline** (`src/services/tools/toolExecution.ts`; https://deepwiki.com/dhanlon-intellica/cc/3.1-tool-infrastructure): find tool by name → unknown name returns `"No such tool available: ${toolName}"` as an error result → Zod parse; failure returns `formatZodValidationError(tool.name, parsedInput.error)` classified `InputValidationError` ("If validation fails, an error is returned to the model immediately") → `validateInput` → `checkPermissions` / `canUseTool` (PreToolUse hooks run here; a hook stop with no message yields `"Execution stopped by PreToolUse hook"`) → `call` with the `ToolUseContext` (abort signal, `readFileState` cache, `getAppState/setAppState`, `contentReplacementState`) → `mapToolResultToToolResultBlockParam` → size budget → `tool_result` in a user message. Timing constants: `HOOK_TIMING_DISPLAY_THRESHOLD_MS = 500`, `SLOW_PHASE_LOG_THRESHOLD_MS = 2000`.

**Read-only is per input, not per tool.** Bash's `isReadOnly` runs `checkReadOnlyConstraints(input, compoundCommandHasCd).behavior === 'allow'` and `isConcurrencySafe` delegates to it (`src/tools/BashTool/BashTool.tsx`). Filesystem tools default to Read = always allow, Write/Edit/Bash = ask (https://deepwiki.com/dhanlon-intellica/cc/3.2-filesystem-and-shell-tools). Edit validates `old_text` "exists exactly once" before applying (same page).

**Registry and count.** `getAllBaseTools()` in `src/tools.ts` returns core tools — Agent, TaskOutput, Bash, Read, Edit, Write, NotebookEdit, WebFetch, TodoWrite, WebSearch, TaskStop, AskUserQuestion, Skill, EnterPlanMode, Brief — plus conditional (Glob/Grep when embedded search is unavailable) and feature-flagged ones (Sleep, Cron*, RemoteTrigger, Monitor, WebBrowser, Workflow, CtxInspect, TerminalCapture). `assembleToolPool()` dedupes by name, built-ins winning. The README count is "~40 implemented capabilities" (https://deepwiki.com/dhanlon-intellica/cc).

**Deferred loading / ToolSearch** (`src/tools/ToolSearchTool/ToolSearchTool.ts`, `prompt.ts`; the wiki mentions the tool at https://deepwiki.com/dhanlon-intellica/cc/3.3-agent-and-orchestration-tools as "A meta-tool that allows the model to search through the available tool definitions"). `isDeferredTool()`: all MCP tools and any `shouldDefer: true` tool are sent with `defer_loading: true`; never deferred are `alwaysLoad` tools, ToolSearch itself, Brief (KAIROS), and Agent (when forking is on). Deferred tools are announced by name only, via a `<available-deferred-tools>` block or a system-reminder. The model fetches a schema with `query`: `select:Read,Edit,Grep` (exact), keywords scored against name parts, description and `searchHint`, `+term` to require a term, `mcp__` prefix matching; `max_results` default 5. Result is an array of `tool_reference` blocks (or a "no matches" text, listing pending MCP servers); the turn boundary message is `'Tool loaded.'` (`TOOL_REFERENCE_TURN_BOUNDARY`, `src/utils/messages.ts`).

**System-prompt guidance on tools** (`src/constants/prompts.ts`): "Do NOT use the Bash tool to run commands when a relevant dedicated tool is provided"; "If you intend to call multiple tools and there are no dependencies between them, make all independent tool calls in parallel"; "Mark each task as completed as soon as you are done with the task. Do not batch up multiple tasks". Internal-only length anchors: "Keep text between tool calls to ≤25 words. Keep final responses to ≤100 words unless the task requires more detail."

**MCP tools** are normalised into the same `Tool` shape (`src/services/mcp/operations/normalization.ts`, https://deepwiki.com/dhanlon-intellica/cc/6-mcp-(model-context-protocol)); outputs are stored "with size validation to prevent context exhaustion" (`src/services/mcp/mcpOutputStorage.ts`, https://deepwiki.com/dhanlon-intellica/cc/6.2-mcp-skills-and-plugin-integration).

## 5. Subagents

**Isolation.** `AgentTool` "uses `createSubagentContext` to generate a scoped `ToolUseContext`"; "while the subagent has its own conversation history, it still reports back to the main application state for task tracking and cost accounting"; each gets a new `QueryEngine` (https://deepwiki.com/dhanlon-intellica/cc/3.3-agent-and-orchestration-tools, `src/Tool.ts:183-192`).

**Input schema** (`src/tools/AgentTool/AgentTool.tsx`): `description` (3–5 words), `prompt`, `subagent_type?`, `model?` (`sonnet|opus|haiku`), `run_in_background?`; swarm extras `name`, `team_name`, `mode`, `isolation` (`worktree|remote`), `cwd`.

**What the subagent gets** (`src/tools/AgentTool/runAgent.ts`): messages = `createUserMessage(prompt)` only (normal path) or, with no `subagent_type`, an implicit _fork_ that "inherits the parent's full conversation context and system prompt" (`forkSubagent.ts`). System prompt = `agentDefinition.getSystemPrompt()` (fallback `DEFAULT_AGENT_PROMPT`) + env details. CLAUDE.md is omitted for definitions with `omitClaudeMd` under flag `tengu_slim_subagent_claudemd` (default true) and git status is omitted for Explore/Plan — the source cites projected savings of "5-15 Gtok/week" and "1-3 Gtok/week" respectively. Tool pool = `resolveAgentTools()` from the definition's allow/disallow lists under its own permission mode (`acceptEdits` by default); Explore disallows Agent, ExitPlanMode, Edit, Write, NotebookEdit and runs "in strict read-only mode" (`src/tools/AgentTool/built-in/exploreAgent.ts`). `maxTurns = override ?? agentDefinition.maxTurns`. Built-ins: Explore, Plan, general-purpose, verification, claude-code-guide, statusline-setup (`built-in/` listing).

**What comes back.** The last assistant text via `extractTextContent()`, plus a trailer: `agentId: <id>` (for SendMessage routing) and `<usage>` tags with tokens/tool calls/duration; one-shot agents (`ONE_SHOT_BUILTIN_AGENT_TYPES = {Explore, Plan}`) omit the trailer "to save tokens (~135 chars per run)" (`AgentTool.tsx`, `constants.ts`). Fork children get a per-child directive that starts with "Scope:" and caps the report at 500 words (`forkSubagent.ts`). The tool prompt tells the parent "The result returned by the agent is not visible to the user. To show the user the result, you should send a text message back" (`src/tools/AgentTool/prompt.ts`).

**Concurrency / nesting.** "No explicit parallel limit"; sync agents block the main loop; `run_in_background: true` returns immediately with `'async_launched'` and an output file, completion arrives as a notification; auto-background after `120_000 ms`; progress hint after `2000 ms`. Nesting is allowed — only fork recursion is guarded (`AgentTool.tsx`). Background agents are `Task`s (`local_agent`, id prefix `a` + 8 random chars, output persisted to disk, states `pending|running|completed|failed|killed`) (https://deepwiki.com/dhanlon-intellica/cc/2.3-task-system). Teammates in swarms message each other with `SendMessage` and share memory via `teamMemorySync` (https://deepwiki.com/dhanlon-intellica/cc/9-multi-agent-and-swarm-system, https://deepwiki.com/dhanlon-intellica/cc/10.4-memory-system).

**Denials inside subagents** get a different message: `'Permission for this tool use was denied... Try a different approach or report the limitation to complete your task.'` (`SUBAGENT_REJECT_MESSAGE`, `src/utils/messages.ts`) — the subagent cannot wait for a user, so it is told to route around.

## 6. Memory and instructions

**CLAUDE.md layering** (`src/utils/claudemd.ts`; https://deepwiki.com/dhanlon-intellica/cc/10.4-memory-system describes CLAUDE.md as "project-specific instructions, build commands, and style guides"). Load order: managed `/etc/claude-code/CLAUDE.md` → user `~/.claude/CLAUDE.md` → project `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/rules/*.md` → `CLAUDE.local.md` → auto-memory entrypoint → team-memory entrypoint. "Files load in reverse priority order—later files receive more attention"; nested-worktree duplicates are skipped. `@path` / `@./rel` / `@~/x` / `@/abs` includes, "leaf text nodes only", `MAX_INCLUDE_DEPTH = 5`, binary extensions rejected. `.claude/rules/*.md` frontmatter `paths:` globs make a rule conditional. Recommended cap `MAX_MEMORY_CHARACTER_COUNT = 40000` per file. HTML comments are stripped. Injected under the header: "Codebase and user instructions are shown below. Be sure to adhere to these instructions. IMPORTANT: These instructions OVERRIDE any default behavior and you MUST follow them exactly as written." Content is cached in bootstrap state (`cachedClaudeMdContent`) "to avoid classifier filesystem loops" (https://deepwiki.com/dhanlon-intellica/cc/2.2-application-state-management).

**Auto-memory** (`src/memdir/memdir.ts`; wiki: `memdir/` "stores structured JSON objects containing the memory content, importance, and timestamp", https://deepwiki.com/dhanlon-intellica/cc/10.4-memory-system). `MEMORY.md` is "an index, not a memory": one line per entry (`- [Title](file.md) — one-line hook`, ~150 chars), truncated at `MAX_ENTRYPOINT_LINES = 200` / `MAX_ENTRYPOINT_BYTES = 25_000` with an appended warning ("lines after 200 will be truncated, so keep the index concise"); topic files carry frontmatter (`name`, `description`, `type` ∈ user/feedback/project/reference). Rules given to the model: "Do not write duplicate memories. First check if there is an existing memory you can update before writing a new one"; don't save derivable project state. Reminders are rate-limited: `TURNS_BETWEEN_REMINDERS: 10`, `TURNS_BETWEEN_ATTACHMENTS: 5`, `FULL_REMINDER_EVERY_N_ATTACHMENTS: 5`, `MAX_MEMORY_LINES: 200`, `MAX_MEMORY_BYTES: 4096` (`src/utils/attachments.ts`). After a user message that looks like a correction, `MEMORY_CORRECTION_HINT` is appended: "The user's next message may contain a correction or preference. Pay close attention — if they explain what went wrong or how they'd prefer you to work, consider saving that to memory for future sessions." (`src/utils/messages.ts`). Retrieval: `findRelevantMemories` runs before each prompt, and `startRelevantMemoryPrefetch` is called from the query loop (https://deepwiki.com/dhanlon-intellica/cc/10.4-memory-system, `src/query.ts`).

**Session memory** (the 12k-token notes file) is described in §3.

**Skills** are directory-loaded markdown commands (`getSkillDirCommands`) expanded into the conversation on invocation, re-injected after compaction under the 25k/5k budgets above (https://deepwiki.com/dhanlon-intellica/cc/7.1-command-registry-and-infrastructure, https://deepwiki.com/dhanlon-intellica/cc/9.2-agent-definitions-and-skills).

## 7. Permissions and approvals

**Modes** (`src/types/permissions.ts`; https://deepwiki.com/dhanlon-intellica/cc/4.1-permission-modes-and-rules): `default` ("Requires manual approval for most tools unless an `alwaysAllow` rule exists"), `plan` (read-only planning), `acceptEdits`, `auto` ("uses classifiers ... to decide if a command is safe to run without prompting"), `bypassPermissions`, `dontAsk`. `ToolPermissionContext` is immutable and carries `mode`, `additionalWorkingDirectories`, `alwaysAllowRules`, `alwaysDenyRules`, `alwaysAskRules`, `shouldAvoidPermissionPrompts`, `prePlanMode` (`src/Tool.ts`). Rules are glob patterns for paths and prefix/regex patterns for shell commands; "shadowed" redundant rules are detected (https://deepwiki.com/dhanlon-intellica/cc/4.1-permission-modes-and-rules).

**Evaluation order** (`hasPermissionsToUseTool`, `src/utils/permissions/permissions.ts`; https://deepwiki.com/dhanlon-intellica/cc/4-permission-system): (1) deny rules → ask rules → `tool.checkPermissions()` → content-specific ask rules that override bypass → bypass-immune safety checks on `.git/`, `.claude/`, config files; (2) mode bypass (`bypassPermissions`; `plan` with bypass available) → whole-tool allow rules; (3) transform remaining `ask`: `dontAsk` → deny; `auto` → classifier (after `acceptEdits`/allowlist fast paths); headless → `PermissionRequest` hooks, then auto-deny. Result is `allow | deny | ask` (`PermissionResult`).

**How a write is gated.** Edit/Write/Bash default to "Always Ask"; the prompt shows a `StructuredDiff` (edits) or the highlighted command (bash); the user can approve, deny, or _modify the tool input_ (https://deepwiki.com/dhanlon-intellica/cc/4.2-auto-mode-classifier-and-ui). In `auto` mode the `yoloClassifier` (non-bash tools; rule sections `allow`, `soft_deny`, `environment`, user rules REPLACE defaults per section) or `bashClassifier` (destructive ops, sensitive network, system config) decides; `alwaysAskRules` still force a prompt (same page; https://deepwiki.com/dhanlon-intellica/cc/4.1-permission-modes-and-rules).

**What the model sees on denial** (`src/utils/messages.ts`): user rejection → `REJECT_MESSAGE`: "The user doesn't want to proceed with this tool use. The tool use was rejected (eg. if it was a file edit, the new_string was NOT written to the file). STOP what you are doing and wait for the user to tell you how to proceed." With a typed reason → same text then "To tell you how to proceed, the user said:\n<reason>". Cancel → `CANCEL_MESSAGE` as an `is_error` tool_result ("STOP what you are doing and wait..."). Rule/headless denial default: "Claude requested permissions to use <Tool>, but you haven't granted it yet." (`permissions.ts`). `DENIAL_WORKAROUND_GUIDANCE`: "You _may_ attempt to accomplish this action using other tools that might naturally be used to accomplish this goal, e.g. using head instead of cat. But you _should not_ attempt to work around this denial in malicious ways...". Denials are also recorded in the result as `permission_denials` (`src/QueryEngine.ts`).

**Denial tracking** (`src/utils/permissions/denialTracking.ts`; wiki: `DenialTrackingState` exists "to prevent infinite loops and inform the auto-mode classifier", https://deepwiki.com/dhanlon-intellica/cc/4.1-permission-modes-and-rules): `consecutiveDenials`, `totalDenials`; `recordSuccess` resets consecutive; `shouldFallbackToPrompting()` when `maxConsecutive: 3` or `maxTotal: 20` is exceeded.

## 8. Hooks / extensibility

**Events** (`src/utils/hooks.ts`; the wiki lists a subset at https://deepwiki.com/dhanlon-intellica/cc/1.2-configuration-and-settings and https://deepwiki.com/dhanlon-intellica/cc/10.6-plugin-system): `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `SessionStart`, `SessionEnd`, `Setup`, `UserPromptSubmit`, `Stop`, `StopFailure`, `SubagentStart`, `SubagentStop`, `PermissionRequest`, `PermissionDenied`, `Notification`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`, `ConfigChange`, `CwdChanged`, `FileChanged`, `InstructionsLoaded`, `Elicitation`, `ElicitationResult`, `PreCompact`, `PostCompact`. Hook kinds: shell command, HTTP, prompt (an LLM judge), agent (`src/utils/hooks/exec{Http,Prompt,Agent}Hook.ts`); an `AsyncHookRegistry` runs some asynchronously.

**Contract.** Exit `0` = success; `2` = blocking error; other non-zero = non-blocking error shown to the user. Default timeout `TOOL_HOOK_EXECUTION_TIMEOUT_MS = 10 min`; SessionEnd `1500 ms` (env override). JSON stdout fields: `continue`, `stopReason`, `decision` (`approve|block`), `reason`, `systemMessage`, `suppressOutput`, `permissionDecision` (`allow|deny|ask`), `hookSpecificOutput`, `additionalContext`, `updatedInput`, `async` (`src/utils/hooks.ts`).

**How output reaches the model.** Exit 0 stdout → a `hook_success` attachment (`content`); non-zero → `hook_non_blocking_error` with `stdout`/`stderr` (user-facing); exit 2 or `decision: block` → a `blockingError` yielded to the model as the tool's error result, with `reason` as the text; `additionalContext` is injected as context; `updatedInput` replaces the tool input before execution; `PreCompact` hook text merges into the compaction prompt (`mergeHookInstructions`, `src/services/compact/compact.ts`); Stop hooks (`handleStopHooks`, `src/query/stopHooks.ts`) can block the turn from ending and feed a reason back, which is how "keep going until X" loops are built. Plugins register commands, agents, output styles, MCP servers and hooks via a Zod-validated manifest (https://deepwiki.com/dhanlon-intellica/cc/10.6-plugin-system).

## 9. Error handling and recovery

- **API retries** (`src/services/api/withRetry.ts`; https://deepwiki.com/dhanlon-intellica/cc/10.1-anthropic-api-client-and-model-management: "Implements `withRetry` logic for transient failures and rate limits (429 errors)"): `DEFAULT_MAX_RETRIES = 10`, exponential from `BASE_DELAY_MS = 500` to `maxDelayMs = 32000`, honours `retry-after`; retried statuses 408, 409, 429, 529 and 5xx, plus `"type":"overloaded_error"`; a "persistent" mode backs off up to 5 min for up to 6 h.
- **Model fallback**: after `MAX_529_RETRIES = 3` consecutive overloads with a `fallbackModel` configured, `FallbackTriggeredError` switches models; dangling tool uses get `"Model fallback triggered"` error results (`src/query.ts`).
- **Context overflow on output**: a 400 matching `"input length and max_tokens exceed context limit: {input} + {max} > {limit}"` is parsed and `max_tokens` is lowered, never below `FLOOR_OUTPUT_TOKENS = 3000` (`withRetry.ts`).
- **Prompt too long**: reactive compaction, head truncation (§3), then `reason: 'prompt_too_long'`.
- **Truncated output**: 3 "Resume directly" continuations (§2).
- **Malformed tool input**: Zod error text returned as an error result; unknown tool name returned as an error result; loop continues (`src/services/tools/toolExecution.ts`). Structured-output mode: 5 retries then `error_max_structured_output_retries`.
- **Compaction failure**: 3 consecutive failures trip the breaker; the session keeps going without compaction (`autoCompact.ts`).
- **Interrupts**: abort signal → every executing tool cancels; missing results synthesised; `StopFailure` hooks run on API-error termination (`src/query.ts`).
- **Escalation to a human**: nothing escalates to another model except the 529 fallback; everything else becomes an error result the model reads, or a permission prompt the user answers.

## 12. What does not transfer to a 4k on-device model, and why

1. **Verbatim history with buffers of 13k/20k tokens.** CC keeps the whole conversation until ~187k tokens and then summarises; Goliath's entire budget is smaller than CC's _buffer_, so the brief must replace history every step rather than at a threshold. (`src/services/compact/autoCompact.ts`)
2. **The nine-section, up-to-20k-token summary.** `<analysis>` + nine sections is a document, not a brief; a 3B model at 4k cannot produce or consume it. Keep the four-slot 60-word brief. (`src/services/compact/prompt.ts`, `COMPACT_MAX_OUTPUT_TOKENS`)
3. **Post-compaction re-injection budgets (50k tokens of files, 25k of skills).** There is no room; Goliath re-injects one or two compressed results at most (#9). (`src/services/compact/compact.ts`)
4. **The 10k–40k-token verbatim tail after session-memory compaction.** Same reason. (`sessionMemoryCompact.ts`)
5. **Parallel tool calls and the concurrency partitioner.** Apple's session is one request in flight and CC's batching (`isConcurrencySafe`, max 10, `StreamingToolExecutor`) presumes many; Goliath stays one-step-one-tool. The per-input `isReadOnly` predicate still transfers (#12). (`src/services/tools/toolOrchestration.ts`)
6. **ToolSearch / `defer_loading`.** It exists to fit 40+ schemas plus MCP into a 200k prompt; there is no `defer_loading` on-device and the conductor cannot hold schemas anyway. Goliath's worker-gets-one-schema design already solves the problem ToolSearch solves. (`src/tools/ToolSearchTool/ToolSearchTool.ts`)
7. **Fork subagents sharing the parent's full context for cache-identical prefixes.** Forking copies a huge context and relies on server prompt caching; Goliath's parent context is a brief, and there is no server cache to share. (`src/tools/AgentTool/forkSubagent.ts`)
8. **LLM permission classifiers (`bashClassifier`, `yoloClassifier`).** An extra model call per tool on a serial 3B model doubles step latency, and a 3B model is a poor safety judge; use static rules + confirmation (#16). (https://deepwiki.com/dhanlon-intellica/cc/4.2-auto-mode-classifier-and-ui)
9. **Extended thinking and 64k escalated output.** No thinking mode; outputs are hundreds of tokens. (`ESCALATED_MAX_TOKENS`, https://deepwiki.com/dhanlon-intellica/cc/2.1-queryengine-and-llm-interaction)
10. **Ten-retry exponential backoff with 5-minute persistent mode.** On-device errors are deterministic (guardrail refusals, context overflow), not transient rate limits; retry once, then escalate — which Goliath already does. Keep only the "3 consecutive → fallback" idea (#22). (`src/services/api/withRetry.ts`)
11. **Server-side `context_management` / `clear_tool_uses`.** An Anthropic API feature; Goliath must clear client-side (#2). (`src/services/compact/apiMicrocompact.ts`)
12. **Usage-based token counting and cache-break detection.** Apple FM exposes no `usage` or cache fields; estimate (#5) and skip cache telemetry. (`src/utils/tokens.ts`; https://deepwiki.com/dhanlon-intellica/cc/10.1-anthropic-api-client-and-model-management)
13. **Shell/HTTP/agent hooks with 10-minute timeouts.** Mobile has no shell and no long-running background processes; keep hooks as synchronous in-process functions (#17). (`src/utils/hooks.ts`)
14. **Persisting 64 MiB outputs to disk and telling the model the path to `Read` later.** The model cannot page through large files; the id-plus-slice store (#10) must return slices of ~200 tokens, not a path. (`src/tools/BashTool/BashTool.tsx`, `src/utils/toolResultStorage.ts`)
15. **CLAUDE.md layering with 40k-char files and five levels of `@include`.** Standing instructions for Goliath must be a few hundred tokens and go to the conductor only; layering can survive as concatenation order, not as budget. (`src/utils/claudemd.ts`)
16. **Background session-memory agent.** CC updates its 12k-token notes with a forked agent while the main loop continues; with one request in flight the scribe must run inline between steps and stay tiny. (`src/services/SessionMemory/sessionMemory.ts`)
17. **Structured-output enforcement by five retries with a synthetic tool.** Goliath has guided generation, so schema failures are rare; the residual failure is semantic (wrong tool, wrong step), and one retry with the validation error (#13) is the right budget. (`src/QueryEngine.ts`)
18. **Unbounded main loop / `maxTurns: 200` for forks.** Each Goliath step costs a fixed ~300-token overhead in a 4k window, so a hard step cap (~10) is a correctness requirement, not a safety net (#20). (`src/query.ts`, `forkSubagent.ts`)
19. **Denial-workaround guidance ("use head instead of cat").** Inviting a 3B model to find alternative tools after a refusal encourages the very repeat-call loops Goliath escalates on; use the STOP wording only (#14). (`DENIAL_WORKAROUND_GUIDANCE`, `src/utils/messages.ts`)
20. **Ink permission UIs, structured diffs, bridge `control_request` protocol.** The _concepts_ (show the exact write before confirming; let the user edit the arguments) transfer to the RN confirm sheet, but none of the transport or rendering does. (https://deepwiki.com/dhanlon-intellica/cc/4.2-auto-mode-classifier-and-ui, https://deepwiki.com/dhanlon-intellica/cc/11.2-output-and-streaming)
