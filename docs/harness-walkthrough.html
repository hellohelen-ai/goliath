Understand the machinery

A small model.
A careful loop.

The model proposes the next step. The harness validates it, checks permissions, runs your code, and decides what the model sees next. An agent turn is several small requests with explicit boundaries.

An interactive explanation of this checkout. The examples below are scripted illustrations, not live model calls or performance measurements.

Your app

Owns screens, user approval, tool functions, and storage connections.

→
The harness

Owns conversation queues, prompts, validation, the loop, and budgets.

⇄
The model

Proposes plans and arguments, writes replies, and sometimes summarizes.

              04What went wrong in the screenshot?
            
      
          
      
          
      
            
      
              The lookup worked; the planner kept asking for it.
              
      
                The first listTasks call returned the tasks. An identical second call
                reused the result; the third selection hit repeated-tool-call. The
                harness then asked for a best-effort answer, which is why useful task names appeared
                under a warning.
              
      
              
      
                What is fixed here: that partial reply and its tool evidence now
                survive into the next turn, explicitly marked incomplete. The UI says “Stopped a
                repeated step.” The existing duplicate guard still prevents re-execution; we cannot
                promise the model will stop proposing a bad plan.
              
      
            
      
            
      
              The follow-up was refused before a tool ran.
              
      
                The provider reported “Detected content likely to be unsafe” during planning. The
                old classifier treated that wording as a generic model error, and the app
                substituted “Try asking for one smaller step.” Neither the list nor the completion
                tool ran in that turn.
              
      
              
      
                What is fixed here: the native error is classified as a refusal,
                including wrapped causes. The app says “Apple Intelligence declined this request. No
                action ran.” It doesn’t silently retry the refusal or route it to the cloud.
              
      
            
      
            
      
              Valid JSON is only one part of a correct decision.
              
      
                A plan can be well-formed yet choose the wrong tool. A search argument can pass its
                string schema yet contain the wrong query. Schema validation cannot establish that
                the model understood the user.
              
      
              
      
                What is fixed here: a native “Failed to deserialize a Generable
                type from model output” error follows the existing bounded validation path: one plan
                retry, no execution of invalid arguments, and at most one structured-answer retry.
                This doesn’t cure semantic errors or a provider call that never resolves.
              
      
            
      
            
      
              “On-device” describes where it ran, not whether it succeeded.
              
      
                The old footer used a checkmark even when zero steps completed and no answer was
                returned. Now an unfinished outcome uses a warning icon and an “Unfinished” label,
                with a cause-specific explanation.
              
      
              
      
                If a write already ran before a later failure, the message warns that earlier
                actions may have completed. A retry must never be presented as though the earlier
                action definitely did nothing.
              
      
            
      
            
      
              What would make the live model more reliable?
              
      
                Keep a repeatable device evaluation set for lookup, follow-up, approval, refusal,
                pagination, and malformed output. Inspect generated plans and arguments, tighten
                descriptions and examples against those failures, and measure each change. A model
                timeout needs explicit cancellation behavior and must not expire while a person is
                deciding an approval.
              
      
              
      
                Scripted tests verify the harness’s decisions. Direct simulator tool checks verify
                native storage. Real model-driven runs are still needed to measure whether the model
                chooses useful actions.
              
      
            
      
          
      
        
      
        
      
          
      
            
      05Where the code fits
      
          
      
          
      
            
      // Base harness
const agent = createAgent({
  model: () => apple(),
  tools: { listTasks, completeTask },
  memory: storage.memory,
  confirm: showApproval,
});

await agent.run("List my open tasks.", {
  conversationId: "travel",
});
      
            
      
              
      agent.run() is the base API.
      
              
      
                The example’s runtime.ask() wraps it with cancellation and approval
                callbacks. useConversations() connects that runtime to the Zustand
                conversation store. Screens render state; they don’t run a second agent loop.
              
      
              
      
                One agent can serve many conversation IDs. Runs within an ID queue in order;
                different IDs can run concurrently. A model factory can create a fresh model/session
                for each generation. Goliath carries the context between those calls.
              
      
              
      
                Hooks can adjust each phase. They don’t grant a model direct access to your device
                or silently authorize writes.
